Database migration rollback checklist

Use this before approving a production database migration. Keep database URLs, credentials, connection strings, dumps, customer rows, raw logs, account IDs, PII, and production data out of public tools.

1. State the migration scope

  • Framework, command, migration ID/version, environment, table, column, index, and data/backfill scope
  • App version or deploy order tied to the migration
  • Named owner and reviewer

2. Check backup and compatibility

  • Snapshot, backup, restore owner, and recovery decision path
  • Expand-contract compatibility, nullable/default behavior, dual-write/read path, and backfill plan
  • Production, staging, or sanitized schema validation context

3. Review runtime and rollback risk

  • Lock, long-running query, transaction, DDL, concurrent index, downtime, and maintenance-window risk
  • Rollback, reverse/down migration, previous version, restore plan, and failed-migration resolution path
  • Drift, manual hotfix, schema history, migration table, or edited/deleted migration status

4. Validate and protect private data

  • Run migration status, smoke test, query checks, metrics, monitoring, and error-rate review.
  • Avoid reset/drop/recreate/force-apply/no-backup language unless the risk and approval path are explicit.
  • Do not paste database URLs, credentials, connection strings, dumps, customer rows, raw logs, account IDs, PII, or production data.
